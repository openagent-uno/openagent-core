# Embedding beta 183

A required module can own a local MCP process that takes longer than the first
handshake deadline to initialize. Module startup now waits for the retry series
the pool has already scheduled. The module registers its discovered tools once
all its required sources are ready. Vault derives trusted effects from that
inventory, and each call checks current authorization. Startup fails on a
permanent error or when the retry series is exhausted.

A successful discovery can return an empty catalog. The source then reports
`ready` with zero tools and its module can publish the service. Cancelling a
multi-source startup closes the processes it started. Cancelling a reload
keeps healthy, unchanged connections and closes those acquired by the attempt.
Startup and recovery send no tool calls.

In a local `openagent serve` test of the retry change, the first launch of the
packaged Node vault was delayed by 35 seconds. Server `1.1.9b118` with Core
`1.1.0b179` and server `1.1.9b119` with Core `1.1.0b182` both exited with
status 1. With the same 30-second handshake deadline, server `1.1.9b119` with
the patched Core reached HTTP 200 on the gateway health check after 39.28
seconds, following vault recovery.

See the [module contract](../modules-v1.1.md) and [MCP retry timing](../mcp-transport-recovery.md#bounded-reconnect-for-configured-sources).
