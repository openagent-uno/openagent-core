# Core beta40: deterministic SQLite handle lifetime

Capability-host `1.0.0b3` closes every local audit, idempotency and mutation-lease
SQLite connection at the end of its transaction, including errors during
connection setup. The previous `with sqlite3.Connection` scopes committed or
rolled back transactions but left connection lifetime to Python's collector.
On Windows, retained reference cycles could keep database/WAL files locked even
after the capability host and its owned MCP provider had shut down. A real
Windows release test exposed the defect while cleaning its owned temporary home.

All 15 ledger transaction scopes now share an explicit context manager. It
preserves SQLite commit/rollback behavior and closes the connection in `finally`.
Tests retain connection objects and disable cyclic collection, check public audit,
idempotency/replay and lease operations, exercise commit/rollback and setup
failure, and require the actual handles to be closed before file deletion.
No garbage-collection workaround or platform skip is used.

Core, SQLite adapter, gateway and Python SDK advance to `1.1.0b40`. Their Core
pins stay aligned. The Core and Python SDK `capabilities` extras require
`openagent-capability-host==1.0.0b3`; Core's base dependencies remain empty.
Capability-host still consumes tool protocol `1.0.0b2`. The independent modules
retain their beta37 public versions and artifact bytes. All five cohort wheels
are built from a clean committed source tree, with source/wheel hashes in the
release manifest; earlier public beta38/beta39 artifacts remain immutable.

The capability-host change requires rebuilding Host bundles and consumers with
the new dependency. Earlier Host candidates containing capability-host beta2
cannot qualify the corrected release. Native/browser implementation versions and
OS permission boundaries are unaffected. Signed six-platform Host qualification,
SDK aggregate publication and product deployment remain separate gates.
